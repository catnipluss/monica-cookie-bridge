# 开发笔记：技术决策与踩坑记录

本项目在开发过程中实测得出的结论，供使用者和二次开发者参考。按时间顺序累积，均为单机实测，环境不同结论可能有差异。

## 网络

### 必须直连上游（`trust_env=False`）

桥最初 httpx 走默认环境配置，被本机系统代理环境变量劫持，所有上游请求绕道 `127.0.0.1:<proxy>`，表现为大面积 ReadTimeout / 502。排查时 curl 一直正常（curl 默认不吃这些变量），导致真凶被掩盖很久。

**教训**：本地常驻服务发外部请求时，显式声明直连，不依赖进程环境；诊断时用 `curl --noproxy "*"` 对照，能快速分辨"服务问题"还是"代理链路问题"。

### Chrome User-Agent 是必需的

用 Python 默认 UA 请求上游，部分模型会被静默挂起（不响应也不报错）。带上与浏览器一致的 UA 后行为与网页一致。

### TLS 指纹伪装方案不可取

曾尝试 curl_cffi 的 chrome 指纹伪装，结果触发上游连续连接重置和全量 502，比不伪装更糟。结论：普通 httpx + 真实浏览器 UA 即可，**不要做指纹级伪装**。

## 稳定性

### 上游存在轮换式限流

Monica 后端会随机挂起部分请求（长时间无响应）或返回 502，过几分钟自行恢复，且"哪个模型被限"是轮换的——超时≠模型坏。

**对策**：桥在**首字到达前**失败自动快速重试（最多 4 次、短退避）；已经开始输出的流不重试（半截回复无法回放给客户端）。401/403 属凭据问题，重试无意义，直接抛出。

### 富对话历史必须宽容处理

严格的 OpenAI 兼容服务假设 `content` 是纯文本，但真实客户端（如 DSH）的对话历史包含 `content: null` + `tool_calls`、`tool` 角色消息、多模态块。逐字校验直接 400，长对话（有过工具调用）必踩。

**对策**：所有非文本内容降级为文字描述（`[tool result <id>]`、`[assistant requested tool calls: ...]`、`[non-text block '<type>' omitted]`），保留语义、不丢上下文。

## 会话与凭据

### Cookie 无法（也不应）从浏览器自动提取

Chrome/Edge 新版 Cookie 加密与浏览器实例绑定，复制数据库或外部解密都走不通——这是浏览器**有意为之的安全设计**。本项目因此选择最保守的方案：用户自己在 `/setup` 页面粘贴 Cookie 头，桥不碰浏览器、不做任何提取。

### API key 持久化

key 最初每次启动随机生成，导致重启桥就要改一遍客户端配置。现在 key 首次生成后写入本地文件（`.bridge-api-key`，已 gitignore），重启不再轮换。

## 测试

- 用 `httpx.MockTransport`（经 `MONICA_TRANSPORT_FACTORY` 钩子注入）模拟上游，20 个测试全部离线运行，不发真实请求、不含真实凭据。
- 测错误路径时注意：如果被测代码有重试退避，测试里应把重试次数调成 1，否则每个失败用例空等数秒甚至超时。
